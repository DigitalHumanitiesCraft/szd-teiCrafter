# Data

The editor works on documents of the Stefan Zweig Digital collections in machine-generated TEI, with facsimiles from GAMS and person identifiers from the edition's person index and the GND.

## Subject

The material is the holdings of Stefan Zweig as kept by the Literaturarchiv Salzburg, transcribed by szd-htr in four collections, correspondence, life documents, works and essay files, whose TEI profiles differ. Works almost always carry a `standOff` with a `listPerson` whose persons have a GND `idno`, essay files mostly do, life documents partly, and correspondence never. No raw document carries `persName` in its body, so the `standOff` persons are not linked to the text. Length ranges from a single page to notebooks and registers of more than a hundred pages. The example letter `o_szd.1222` is a typed business letter to his secretary in Vienna, dated Nice, 4 January 1935, signature SZ-SAM/B7.52, with handwritten additions and a postscript.

## Sources

- Working set: about ten documents per collection under `data/<collection>/`, chosen for the variety of their TEI profiles (single page and very long, typed and handwritten, with and without `standOff`, clean and dense with markers, several languages). `tools/working-set.json` lists each document with the reason for its choice and the documents excluded with their reason. The example letter stays at `data/o_szd.1222.tei.xml` as the start document.
- Import: `tools/import-working-set.mjs` copies the TEI byte-exact from `results/<collection>/` of a local szd-htr clone and writes `data/IMPORT.md`. Most szd-htr results are gitignored and regenerated by its pipeline, so the record names per document the szd-htr commit read from, whether the file is tracked there, the import date and the SHA-256 of the copied bytes, which identifies the uncorrected original. A rerun keeps files that differ from their source, because they have been corrected here (ADR-010).
- Pipeline: szd-htr transcribed the page images with gemini-3.1-flash-lite-preview into Page-JSON and converted that into TEI. Each header states that structure and transcription are unreviewed. Licence CC BY 4.0 per Stefan Zweig Digital, with attribution in `data/NOTICE.md` for the example letter and in `data/IMPORT.md` for the working set.
- Document index: `data/index.json`, generated by `tools/build-document-index.mjs` from the working set and the files, lists per collection each document with path, object id, shelf mark (`idno[@type="shelfmark"]`, empty where the document has none, which holds for all letters of the working set), title (the first `title` with markup dropped and character references resolved, so that `o_szd.100` reads „Agreement Longmans, Green & Co. Inc.“ as the editor shows it), number of pages, number of open spots and working state (`revisionDesc/@status` read as the editor reads it, `draft` where absent). The editor reads it for the document list instead of every file. It is rebuilt after an import and after commits that change a document's state.
- Facsimile: the IIIF Presentation 2 manifest `https://gams.uni-graz.at/o:szd.NNNN/sdef:IIIF/getManifest`, whose canvases point to IIIF Image API level 2 services under `https://gams.uni-graz.at/iiif/`. GAMS answers with permissive CORS headers. Images are not copied into the repository.
- Authority by part: SZD-split holds the authoritative header and catalogue description, this repository the corrected transcription body, and both are to be merged and validated together against the project ODD kept in SZD-split (ADR-010). Until that merge is built, the header in the files here is the converter's.
- Places: the GND type PlaceOrGeographicName through lobid-gnd, queried only on request. GeoNames is not used, because its API needs a registered user name.
- Persons: the person index of Stefan Zweig Digital (`o:szd.personen`, CC BY 4.0), prebuilt into `data/register/szd-persons.json` with its own `NOTICE.md`, and the GND through the lobid-gnd search API for persons outside the index, queried only on request.

## Model

The TEI follows the szd-htr conversion. `teiHeader` carries the title (description, date and signature) and `idno[@type="objectId"]` (`o_szd.NNNN`), `langUsage/language/@ident` names the language, `facsimile` holds one `surface` per page with a `graphic/@url` to the GAMS image, and `text/body/div[@type="document"]` holds paragraphs with `lb` and a `pb[@facs]` per page. The raw files carry no `revisionDesc`. Acceptance in the editor adds one (ADR-011).

The HTR (Handwritten Text Recognition) output marks open editorial work in plain text rather than in elements:

- `~~…~~` for a deletion, the later `del`.
- `[?]` after an uncertain reading, the later `unclear`.
- `{…}` for a handwritten addition, the later `add`.
- `[...]` for an illegible or omitted passage, also as `[...n...]` with an estimated length, the later `gap`. It is concentrated in a few documents of the working set, one notebook among the works above all.
- `[?]` standing alone, not attached to a word, for an unreadable word, and `[?n?]` for several. Some letters and notebooks carry hundreds of them.
- Marker syntax the wraps cannot resolve, a leftover `~~`, `{` or `}`, mostly from a deletion or addition that runs over a line break, as in one life document, two works and one essay file of the working set.
- Bracketed remarks of the transcription, such as `[Randnotiz links:]`, `[Handschriftliche Notiz am linken Rand:]`, `[Durchgestrichen: harte]`, `[eingefügt: hinaus]` and `[Unterschrift unleserlich]`. Brackets attached to a word, such as the supplied letters in „G[ro]d“, a number such as `[3500]`, and brackets in header titles such as „Briefregister [I]“ are no remarks.

The editor counts all of these as open spots, searched in the transcription outside the header and comments, so a document carrying any of them is not ready for acceptance. It offers actions for the first three. A leftover marker is resolved by hand in the XML view. The other kinds have no encoding rule yet, so F8 selects them and the menu names the open rule, see [plan](plan.md#s4-editorial-rule-layer).

The editor adds `persName` whose `@ref` points to the person index entry, or to the GND for persons outside the index, `placeName` with a GND reference or, not yet linked, without `@ref`, and `date` with ISO values in `@when`, `@from` and `@to` or `@notBefore` and `@notAfter`. Which actions exist and which elements and attributes they write is data in `data/actions.json`, checked against TEI All when the editor loads (ADR-013).

## Limits

- The transcription is unreviewed LLM (Large Language Model) output and contains reading errors. Because the HTR markers are plain text, validation against TEI All cannot see them, so a valid document may still hold open work.
- Persons in neither the person index nor the GND have no identifier source.
- Some GAMS manifests are invalid JSON, because quotation marks in range labels are not escaped (`o_szd.67`, `o_szd.174`). Their facsimile cannot load, so the two documents were left out of the working set.
- The manifest may hold a different number of canvases than the TEI has pages. `o_szd.2934` has a sixth canvas after the five pages of its TEI. The editor turns to the canvas at the position of the preceding `pb`, so a surplus canvas at the end only adds a page without text, while one before the end would shift text and image apart.
- A few life documents in szd-htr outside the working set carry `language/@ident="deu"` where the others use `de`.
- Not every szd-htr result is well-formed. `results/aufsatzablage/o_szd.2780.tei.xml` fails to parse. The import tool checks the object id and `pb/@facs` but does not parse the file, so a document is parsed before it enters the working set.

## Authority data and links

- Person index entries in `persName/@ref`, form `#SZDPER.{n}` as in the holdings. The GAMS RDF transform (`szd-TORDF.xsl` in SZD-split) appends `@ref` to `https://gams.uni-graz.at/o:szd.personen`, so a full URI would yield a broken resource. The editor still reads the full URI that its earlier versions wrote.
- GND URIs for persons outside the index, form `http://d-nb.info/gnd/{id}` as in the holdings.
- IIIF manifests derived from the object id by `source.manifestFor` in `js/source.js`.
